# AI Infra Platform · Data Layer

数据层契约：schema、迁移、种子数据、数据字典。

## 为什么单独成一个仓库

schema 是**独立于应用的契约**。

把它放在后端仓库里，它会跟着后端代码的节奏走——后端重构一次，schema 就被顺手动一次。久而久之，没人说得清"这张表为什么长这样"。

独立出来后：

- 它能有自己的版本号与演进节奏
- 它明确承认自己有多个消费者，而不是某一个服务的私有物
- 每次变更可以被单独审查、单独测试、单独回滚

## 它不做什么

- **不含业务逻辑**。这里只有 DDL 与迁移脚本
- **不依赖任何应用代码**。任何语言的任何服务都可以读它
- **不做数据归档与备份策略**。那是运维层的事

## 表清单

| 表 | 职责 | 主要消费者 |
|----|------|-----------|
| `backend` | 推理后端实例注册表，系统里"有哪些后端"的唯一真相 | 控制层写、调度器读 |
| `model` | 模型目录 | 控制层写、调度器读 |
| `backend_model` | 后端与模型的多对多关系，含加载状态 | 调度器读 |
| `backend_health_check` | 健康检查历史，用于可用性分析 | 控制层写、观测层读 |
| `request_log` | 每个推理请求的观测数据 | 控制层写、观测层读 |
| `routing_decision` | 每次路由的决策依据与结果 | 控制层写、观测层读 |
| `api_key` | 调用方密钥，只存哈希 | 接入层读 |
| `schema_migration` | 迁移版本记录 | 迁移工具读写 |

## 迁移纪律

1. **只增不改**。已执行的迁移文件永不修改，改错了就再加一个修正迁移
2. **单事务**。每个迁移文件在一个事务内执行，失败整体回滚
3. **破坏性变更三步走**：先加新列并双写 → 回填历史数据 → 确认无依赖后再删旧列
4. **可重复执行**。迁移脚本重复运行不应报错

## 目录

```
migrations/     按序号排列的迁移文件，只增不改
seeds/          开发与测试用种子数据
docs/           数据字典
```

## 使用

```bash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f migrations/001_init.sql
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f seeds/001_local_dev.sql
```

`ON_ERROR_STOP=1` 不可省略。没有它，psql 遇到错误会继续往下执行，你会得到一个半残的库。
